📝 LoRA 高效微调

像贴便签一样轻量级的微调方法

🎯 问题：全参数微调的代价

全参数微调对于大模型来说代价极高：

问题说明
显存巨大 7B 模型全参数微调需要 80GB+ 显存（2张 A100）
存储昂贵 每个 checkpoint 都得存完整的模型权重
灾难性遗忘 全参数微调容易丢失预训练学到的大量知识
资源浪费 预训练的 99.9% 知识都要重新训练
💡 LoRA 的核心思想

不要修改原权重，而是注入"补丁"

全参数微调
W = W - lr×∇W
直接修改原始权重
↓
LoRA
W' = W + ΔW
只训练 ΔW = BA

🔧 LoRA 原理：低秩矩阵分解

LoRA 在权重矩阵 W 旁边添加两个小矩阵 A 和 B：

原始权重
W
d × k
冻结不训练
+
LoRA 新增
B × A
(r×k) + (d×r)
r = 低秩 (r << d,k)

输出计算：

h = Wx + BAx = (W + BA)x
💡 直观理解：参数量压缩

假设 W 是 4096×4096 的矩阵：

全参数微调
4096 × 4096
= 16M 参数
LoRA (r=8)
4096×8 + 8×4096
= 64K 参数
压缩比
64K / 16M
≈ 1/256

🔄 LoRA 训练流程

1. 冻结
原始权重 W 冻结
→
2. 初始化
A 随机，B 零初始化
→
3. 训练
只更新 A 和 B
→
4. 合并
W' = W + BA

前向传播计算：

# 原始路径（冻结）
h1 = W @ x

# LoRA 路径（训练）
h2 = B @ A @ x

# 合并输出
h = h1 + scaling * h2

💻 LoRA 代码实现

PyTorch LoRA 层
import torch
import torch.nn as nn
import torch.nn.functional as F

class LoRALinear(nn.Module):
    def __init__(self, in_features, out_features, r=8, alpha=16):
        super().__init__()
        self.r = r
        self.alpha = alpha
        self.scaling = alpha / r

        # 冻结原始权重
        self.weight = nn.Parameter(
            torch.randn(out_features, in_features)
        )
        self.weight.requires_grad = False

        # LoRA 低秩矩阵（A 随机初始化，B 零初始化）
        self.lora_A = nn.Parameter(torch.randn(r, in_features))
        self.lora_B = nn.Parameter(torch.zeros(out_features, r))

    def forward(self, x):
        # Wx：原始路径（冻结）
        # BAx：LoRA 路径（训练）
        return F.linear(x, self.weight) + \\
               self.scaling * F.linear(x, self.lora_B @ self.lora_A)

🔀 LoRA 变体

变体特点适用场景
QLoRA 4bit 量化原始权重 + LoRA，大幅降低显存 消费级显卡可微调 7B 模型

LoRA+ A/B 用不同学习率和初始化 稳定性和效果优化

📦 Batch LoRA 和 Multi-LoRA

📊 核心概念对比

维度Batch LoRAMulti LoRA
核心含义 一次推理中批量处理多个不同 LoRA 的请求 一个模型同时服务/组合多个 LoRA 适配器
应用场景 高并发服务，不同用户用不同 LoRA 多任务、多风格、能力组合
解决痛点 切换 LoRA 开销大，无法批处理 单个 LoRA 能力有限，需要组合
并行方式 请求级并行（不同请求用不同 LoRA） LoRA 级并行/组合（一个请求用多个 LoRA）
1. Batch LoRA：批量处理不同 LoRA 请求

问题：传统方式无法批量处理使用不同 LoRA 的请求

❌ 传统方式（串行）

请求 A (LoRA-编程助手) → 推理 → 返回
请求 B (LoRA-翻译助手) → 推理 → 返回
请求 C (LoRA-写作助手) → 推理 → 返回

无法合并成一个 batch！
因为每个请求的 LoRA 权重不同

✅ Batch LoRA（并行）

┌─────────────────────────────────────────┐
│  请求 A (LoRA-编程)  ─┐                  │
│  请求 B (LoRA-翻译)  ─┼─→ 一次前向传播  │
│  请求 C (LoRA-写作)  ─┘   返回各自结果  │
└─────────────────────────────────────────┘

共享基础模型，动态路由 LoRA

🔧 技术实现

  • 共享基础模型权重（冻结）
  • 每个 token 位置记录对应的 LoRA ID
  • 计算 attention 时动态路由到对应的 LoRA 权重
  • 典型实现：vLLM、LoRAX、S-LoRA
2. Multi LoRA：组合多个 LoRA 能力

问题：单个 LoRA 只学了一种能力，复杂任务需要多种能力

📋 场景示例

用户问："用李白风格写一段关于量子力学的诗"

需要的能力：
├── 量子力学知识 → LoRA-科学
├── 李白诗歌风格 → LoRA-文学
└── 诗歌创作技巧 → LoRA-创作

单个 LoRA 无法同时满足！

方案一：LoRA 组合（加权融合）

W = W₀ + α₁×B₁A₁ + α₂×B₂A₂ + α₃×B₃A₃
        ↑         ↑         ↑
     LoRA-科学  LoRA-文学  LoRA-创作

通过调整权重 α 控制各 LoRA 的影响程度

✅ 简单直接，推理时只加载融合后的权重

⚠️ 需要手动调整或搜索最优权重

方案二：Multi-LoRA Adapter (MoA)

输入
x
→
基础模型
W₀
→
LoRA₁
LoRA₂
LoRA₃
并行处理
→
加权聚合
Σ αᵢhᵢ
→
输出

✅ 多个 LoRA 并行处理，结果加权聚合

方案三：动态路由（类似 MoE）

输入 → 路由网络 → 判断该用哪些 LoRA
              ↓
        激活 LoRA₁ + LoRA₃（跳过 LoRA₂）
              ↓
        只计算被激活的 LoRA，节省计算

✅ 自动选择相关 LoRA，计算高效

⚠️ 需要训练路由网络

LoRAHub

自动搜索最优 LoRA 组合权重

MoA

多适配器混合架构

S-LoRA

支持数千个 LoRA 并发服务

📊 Batch LoRA vs Multi LoRA 总结

维度Batch LoRAMulti LoRA
目标 提高推理吞吐量 增强模型能力
LoRA 关系 独立，各服务各的请求 协作，共同处理一个请求
技术难点 动态权重路由、显存管理 权重融合、冲突避免
应用场景 SaaS 平台多租户 多技能 Agent、复杂任务

🎚️ 秩 r 怎么选？

r 值参数量适用场景
r=2 极少 简单任务、灾难性遗忘风险高
r=4~8 很少 通用对话、写作（推荐起步值）
r=16~64 中等 复杂推理、代码生成
r=128~256 接近全参 复杂任务、最终任务微调

💡 经验法则：大多数任务 r=8~16 就够用

📝 总结

LoRA = 冻结原权重 + 训练低秩补丁 BA
Batch LoRA = 多个 Adapter 打包推理
Multi-LoRA = 多 Adapter 切换/融合/集成

🎯 LoRA 优势

  • 显存节省：训练参数量减少 100-1000 倍
  • 存储节省：每个 adapter 只需几 MB
  • 防止遗忘：原权重冻结，预训练知识保留
  • 灵活切换：不同任务加载不同 adapter
  • 训练稳定：低秩空间，loss 平滑
