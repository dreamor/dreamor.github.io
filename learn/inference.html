🔮 推理流程 (Inference)

模型是如何"说话"的？

🎯 推理 vs 训练：本质区别

推理和训练的过程有本质区别，理解这个区别很重要：

维度训练 (Training)推理 (Inference)
目的 学习参数（调整权重） 使用参数（生成文本）
梯度计算 需要反向传播计算梯度 不需要梯度，只需前向传播
参数更新 梯度下降更新参数 参数冻结不变
前向传播 整个序列并行计算（teacher forcing） 逐个 token 自回归生成
显存占用 需要存储梯度、优化器状态 只需权重和 KV Cache
💡 为什么推理不需要梯度？

梯度是用于"学习"的，训练时我们需要知道"往哪个方向调整参数"才能让 loss 降低。

推理时模型已经学完了，只需要"用"学好的参数来计算输出，不需要再调整参数，所以不需要梯度。

⚡ 推理的两个阶段：Prefill & Decode

LLM 推理过程分为两个核心阶段，理解它们对优化推理性能至关重要：

🔹 预填充阶段 (Prefill)

处理所有输入 token

  • 输入：用户输入的所有 token（提示词、上下文）
  • 计算：并行计算所有 token 的 attention
  • 输出：第一个生成 token + KV Cache
  • 特点：计算密集型，GPU 利用率高

⚡ 一次性处理完所有输入

🔹 解码阶段 (Decode)

逐个生成输出 token

  • 输入：上一个生成的 token
  • 计算：串行计算，每次只处理 1 个 token
  • 输出：下一个 token，更新 KV Cache
  • 特点：访存密集型，GPU 利用率低

🔄 循环直到生成 [EOS] 或达到长度限制

📊 两阶段对比

维度预填充 (Prefill)解码 (Decode)
处理方式 并行处理所有输入 串行逐个生成
计算特点 计算密集 (Compute-bound) 访存密集 (Memory-bound)
GPU 利用率 高 (80%+) 低 (10-30%)
KV Cache 构建并存储 读取并追加
瓶颈 计算能力 显存带宽
时间占比 ~20% (短输出) / ~5% (长输出) ~80% (短输出) / ~95% (长输出)
💡 为什么解码阶段 GPU 利用率低？

解码阶段每次只处理 1 个 token，但需要从显存读取整个 KV Cache（可能几十 MB）来计算 attention。

计算量很小（1 个 token × 大矩阵），但访存量很大（读取整个 KV Cache），导致 GPU 大部分时间在等待数据，利用率很低。

这就是为什么长上下文模型推理速度慢——KV Cache 越大，每次解码需要读取的数据越多。

🔧 针对两阶段的优化策略

Prefill 优化

  • Flash Attention：减少显存访问
  • Tensor Parallelism：多卡并行计算
  • Chunked Prefill：分块处理长输入

Decode 优化

  • PagedAttention：高效 KV Cache 管理
  • Continuous Batching：动态批处理
  • 投机解码：小模型加速大模型

🔄 完整推理数据流

让我们详细追踪一个推理请求的完整数据流动：

输入: "今天天气"

# Step 1: 输入处理
input_text = "今天天气"
tokens    = tokenizer.encode(input_text)  # [1024, 3056, 5678]

# Step 2: 词嵌入（每个 token → 768 维向量）
embedded = embedding(tokens)
# shape: (3, 768) = 3个token × 768维

# Step 3: 位置编码（叠加 RoPE）
positioned = embedded + position_encoding(3)
# shape: (3, 768)

# Step 4: Transformer 层处理
for layer in range(6):
    positioned = transformer_layer(positioned)
# shape: (3, 768)  ← 每个 token 都变成了包含上下文的向量

# Step 5: 投影到词表
logits = lm_head(positioned[-1])  # 只取最后一个位置
# shape: (1, vocab_size) = (1, 30000)

# Step 6: Softmax + 采样
probs = softmax(logits / temperature)
next_token = sample(probs)  # 采样得到"很"
💡 为什么只需要最后一个 token 的输出？

因为语言的规律是：给定"今天天气"，预测下一个词的是"很"。

前面所有 token 的信息都已经汇聚到了"天气"这个词的位置，通过注意力机制，模型知道"context 截止到'天气'，下一个词应该是什么"。

💡 生成循环的终止条件

循环会在以下任一条件满足时停止：

  • 模型生成了 [EOS] (End of Sequence) token
  • 生成的序列达到了最大长度限制（如 2048 tokens）
  • 内存/时间耗尽（安全保护）

⚡ KV Cache：推理加速的核心

推理时有一个重要的优化技巧：缓存已计算的 Key 和 Value 向量。

❌ 不使用 KV Cache

每个 step 都要重新计算所有历史的 K、V

速度慢，重复计算

# Step 1: 计算 K1, V1
attn([token1])

# Step 2: 重新计算 K1,K2, V1,V2
# K1, V1 被浪费了！
attn([token1, token2])
✅ 使用 KV Cache

新 token 只需计算自己的 K、V

历史缓存复用，速度快

# Step 1: 计算并缓存 K1, V1
K_cache = [K1], V_cache = [V1]

# Step 2: 只计算 K2, V2，拼接缓存
K_all = [K1, K2]  # K1 来自缓存
V_all = [V1, V2]  # V1 来自缓存
已计算 KV
[今天, 天气, 很, 好]
4 × 12 × 128 = 6,144 维度
+
新计算 KV
新词

📐 KV Cache 显存计算

假设 batch=1, seq_len=1024, n_heads=12, head_dim=128, dtype=fp16:

# K cache 和 V cache 各需要
K_cache_size = batch × seq_len × n_heads × head_dim × bytes_per_float
             = 1 × 1024 × 12 × 128 × 2 bytes (fp16)
             = 约 3 MB

# 4K 上下文需要
             = 1 × 4096 × 12 × 128 × 2 bytes
             = 约 12 MB

# 100K 上下文需要
             = 1 × 100000 × 12 × 128 × 2 bytes
             = 约 300 MB

🎲 采样策略详解

模型输出的是概率分布，如何选择下一个词？不同策略效果不同：

模型输出示例："今天天气"后面接的词的概率分布

很好
40%
不错
25%
非常棒
15%
糟糕
5%

🔥 Greedy Search

总是选概率最高的词

next_token = argmax(probs)
# 总是选"很好"

问题：输出单调重复

🎲 Temperature Sampling

通过温度调整分布的"锐利度"

# T > 1: 分布更平滑
# T < 1: 分布更尖锐（更确定）
probs = softmax(logits / T)

T=0.7 常用，平衡创意和连贯

📊 Top-K Sampling

只从概率最高的 K 个词中采样

# K=50: 只考虑前50个词
top_k_probs, top_k_indices = top_k(probs, k=50)
next_token = sample(top_k_indices, top_k_probs)

K太大=无意义，K太小=重复

📈 Top-P (Nucleus) Sampling

累积概率达到 P 时停止扩展候选

# P=0.9: 从高到低累加概率达到0.9的词
# 假设 "很好"(0.4) + "不错"(0.25) = 0.65
# + "非常棒"(0.15) = 0.80
# + "一般"(0.05) = 0.85 还没到0.9
# + "挺好"(0.05) = 0.90 ✓ 停！

动态调整，最常用方案之一

🔍 Beam Search：平衡质量与多样性

Greedy 总是选最优但可能陷入局部最优，Beam Search 是一种"有约束的搜索"：

Beam Size = 3 示例

# 生成"我很___"

# Step 1: 保留概率最高的3个词
BEAM = [("开心", 0.5), ("高兴", 0.3), ("难过", 0.2)]

# Step 2: 每个beam扩展，保留总分最高的3个
扩展1: "我很开心" × 0.5 = 0.15
扩展2: "我很高兴" × 0.3 = 0.09
扩展3: "我很高兴啊" × 0.3 × 0.4 = 0.036
...（省略其他扩展）...

BEAM = [("我很开心", 0.15), ("我很高兴", 0.09), ("我很高兴啊", 0.036)]

Beam Search 在每一步保留 beam_size 条最优路径，而不是只留一条。这样可以找到全局更优的序列。

策略搜索路径质量速度适用场景
Greedy 1 条 ★☆☆ 最快 实时对话，速度优先
Beam Search K 条 ★★★ 中等 需要高质量输出
采样 随机 ★★☆ 快 创意写作，多样性

🛠️ 推理优化技术详解

针对 Prefill 和 Decode 两个阶段的不同特点，有不同的优化策略：

🔹 Prefill 阶段优化（计算密集型）

1. Flash Attention

问题：标准 Attention 需要多次读写显存，中间产生 N² 大小的矩阵

❌ 标准 Attention

Q × K^T → 写显存 (N×N)
→ 读显存 → softmax → 写显存
→ 读显存 → × V → 写显存

多次读写，中间矩阵 O(N²)

✅ Flash Attention

分块 (128×128) 在 GPU SRAM 中：
  Q_block × K_block^T
  → softmax (不写出)
  → × V_block
  → 累加结果

中间结果不写回显存

📊 效果

  • 显存从 O(N²) 降到 O(N)
  • 速度提升 2-4 倍
  • 支持更长上下文（原来 4K → 现在 32K+）

2. Tensor Parallelism（张量并行）

问题：单卡显存/算力不够，无法运行大模型

📐 矩阵拆分原理（4 卡并行）

原始：Y = X × W    (W 是 4096×4096)

拆分：
卡1: Y1 = X × W[:, 0:1024]      ← W 的前 1/4 列
卡2: Y2 = X × W[:, 1024:2048]   ← W 的第 2/4 列
卡3: Y3 = X × W[:, 2048:3072]
卡4: Y4 = X × W[:, 3072:4096]

最后拼接：Y = [Y1, Y2, Y3, Y4]

🔧 应用到 Transformer

每个 Attention Head 分配到不同卡：
卡1: Head 1-8   → 独立计算
卡2: Head 9-16  → 独立计算
卡3: Head 17-24 → 独立计算
卡4: Head 25-32 → 独立计算

最后 all-reduce 汇总结果

✅ 效果：线性扩展，4 卡 ≈ 4 倍速度，支持更大模型

3. Chunked Prefill（分块预填充）

问题：长输入的 Prefill 占用 GPU 太久，阻塞其他请求

❌ 传统方式

用户 A: 100K token 长文档
→ Prefill 需要 2 秒
→ 这 2 秒 GPU 被占满
→ 用户 B、C、D 都在等待

✅ Chunked Prefill

把长 Prefill 切成小块穿插执行：

[Chunk A1][Prefill B][Chunk A2]...
   0.3s      0.1s      0.3s

每个 chunk 让出 GPU 给其他请求

✅ 效果：降低首 token 延迟，提高多用户并发体验

🔹 Decode 阶段优化（访存密集型）

4. PagedAttention（vLLM 核心创新）

问题：KV Cache 显存碎片化，有空间但无法分配

❌ 传统预分配

请求 A (需1000): 预分配4096 → 浪费3096
请求 B (需3000): 预分配4096 → 浪费1096
请求 C (需5000): 预分配4096 → 不够！

总显存够用，但碎片化无法分配

✅ PagedAttention

显存切成固定 block (如16 token)

请求 A: [blk5]→[blk12]→[blk3]
请求 B: [blk7]→[blk8]
请求 C: [blk2]→[blk9]→[blk15]→...

物理不连续，逻辑连续
按需分配，几乎零浪费

✅ 效果：显存利用率从 60% 提升到 95%+，支持更多并发请求

5. Continuous Batching（连续批处理）

问题：传统批处理必须等最慢的请求完成才能处理新请求

❌ 静态批处理

A: [Prefill][Decode][Decode]███ 完成，等待
B: [Prefill][Decode]█████████ 完成，等待
C: [Prefill][Decode][Decode][Decode] 完成

必须等最慢的 C 完成
GPU 在等待时闲置

✅ 连续批处理

t1: [A Prefill][B Prefill][C Prefill]
t2: [A Decode][B Decode][C Decode]
t3: [A Decode][B Decode][C Decode] ← A完成
t4: [D Prefill][B Decode][C Decode] ← 立即补D
t5: [D Decode][B Decode][C Decode] ← B完成
t6: [D Decode][E Prefill][C Decode] ← 立即补E

GPU 始终满载，无等待

✅ 效果：吞吐量提升 3-5 倍，GPU 利用率接近 100%

6. 投机解码（Speculative Decoding）

问题：大模型解码慢，每次只生成 1 个 token

🎯 核心思想：小模型起草 + 大模型批量验证

传统方式（大模型 70B 单独生成）：
Step 1: 大模型生成 token_1 (慢，0.5s)
Step 2: 大模型生成 token_2 (慢，0.5s)
Step 3: 大模型生成 token_3 (慢，0.5s)
总计：1.5s 生成 3 个 token

投机解码（小模型 7B + 大模型 70B）：
Step 1: 小模型快速生成 5 个草稿 (快，0.1s)
Step 2: 大模型一次性验证 5 个 token (0.5s)
        - 前 3 个正确 ✓ → 接受
        - 后 2 个错误 ✗ → 拒绝，大模型生成正确后续
结果：0.6s 生成 3-4 个 token（加速 2-3 倍）
💡 为什么能加速？

验证 n 个 token 和生成 1 个 token 的计算量差不多！因为验证只需要一次前向传播，就能同时检查多个位置的预测。

输出质量和纯大模型完全一样（大模型保证质量）

✅ 效果：2-3 倍加速，输出质量不变，代价是需要额外一个小模型

📊 优化策略总结

优化策略解决问题核心思想阶段
Flash Attention 显存访问慢 分块计算，减少显存读写 Prefill
Tensor Parallelism 单卡算力不足 矩阵拆分到多卡并行 Prefill
Chunked Prefill 长输入阻塞 切分大任务，穿插执行 Prefill
PagedAttention KV Cache 碎片化 分页管理，按需分配 Decode
Continuous Batching 批处理等待 动态调度，即完即补 Decode
投机解码 大模型解码慢 小模型起草，大模型验证 Decode

🔬 推理时的显存去哪了？

训练和推理虽然都用 Transformer，但显存占用的分布完全不同：

训练时显存

  • 模型权重: ~14GB (FP32)
  • 梯度: ~14GB (与权重同尺寸)
  • 优化器状态: ~28GB (Adam m/v)
  • Activations: ~8GB (batch×seq)
  • 总计: ~64GB

推理时显存

  • 模型权重: ~7GB (FP16)
  • KV Cache: ~2GB (batch=1, 4K)
  • 激活值: ~1GB
  • 临时缓存: ~0.5GB
  • 总计: ~10.5GB
💡 为什么推理不需要梯度和优化器状态？

推理时模型只是在"用"学好的参数，不需要"学"，所以不需要：

  • 梯度：用来更新参数，推理不更新参数
  • 优化器状态：Adam 的动量、方差等，仅用于训练时更新

这就是为什么 7B 模型可以在一张 3090 上跑推理（需要 ~10GB），但训练需要 80GB+

📝 总结

推理 = 前向传播 + 自回归生成 + 概率采样

🎯 推理关键点：

  • 不需要梯度：只需前向传播，参数冻结
  • 自回归生成：每个新 token 依赖之前所有 token
  • KV Cache：避免重复计算，是推理加速的核心
  • 采样策略：Temperature/Top-K/Top-P 平衡质量与多样性
  • 显存更小：推理不需要梯度和优化器状态
